# Pi skill inputs

`lead-pi`, `implementer-pi`, `reviewer-pi` and `qa-pi` reuse the contributor
roles and explicitly select skills. They do not select the Claude/Codex plugin
or Claude activity hooks. The recommended profiles retain those selections.

`skills/` is generated, not an independently maintained skill library. Its
canonical sources are the public OpenRig product's bundled `openrig-core`
skills and `.agents/skills/developing-openrig/SKILL.md`. The lock records the
full product commit, bundled plugin version, source paths, file hashes and Git
modes. Complete skill directories include helper scripts and reference files.
The Claude-specific `claude-compaction-restore` skill and plugin hooks are not
selected for Pi. The copied Apache-2.0 license is in `skills/LICENSE`.

Starting with OpenRig 0.6.6, a bundle's explicitly selected skill is used over a
managed catalog copy with the same identity when their contents or permissions
differ. Launch reports `skill_bundle_precedence`; the managed catalog is not
changed. These Pi profiles use the selected generated `skills/` copy.

On earlier versions, a managed catalog at `<skills.root>/catalog.yaml` with
differing copies can cause `skill_identity_conflict` before launch. A fresh
install without a managed catalog is unaffected by that conflict. For those
versions, ask the catalog maintainer to update and commit the conflicting
directory so its files and permissions match `pi-skills.lock.json`; keep this
generated `skills/` tree unchanged.

From this repository's root, with a local clone of the public product:

```sh
python3 tools/generate-pi-skills.py --source /path/to/openrig --check
```

To update, first make the change in the public product. Then regenerate from
its full commit SHA and review the generated diff:

```sh
python3 tools/generate-pi-skills.py --source /path/to/openrig --revision <full-commit-sha>
python3 tools/generate-pi-skills.py --source /path/to/openrig --check
```

The generator reads Git objects at the pin, regardless of the donor's working
tree. It does not run donor code, fetch repositories or install dependencies.
`--check` compares all generated bytes, modes and profile selections with that
source. Edit the canonical source and regenerate rather than editing `skills/`.

These profiles do not select a provider/model or assert native readiness.
Configuration mapping, installed skills and a real Pi session each need their
own checks. A filesystem projection result is not a native provider result.
